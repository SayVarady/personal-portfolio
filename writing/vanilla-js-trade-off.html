Vanilla JS Over a Framework: A Trade-off I Keep Revisiting

Decision Trade-off

I write Vue every day at work. Components, reactivity, the whole ecosystem — it's second nature at this point. So the obvious choice for a personal portfolio was Vue too. I didn't do that, and I still go back and forth on whether it was right.

The Decision

This site is plain HTML, CSS, and vanilla JavaScript — no build step, no framework, no dependencies beyond a font and an icon CDN. The custom cursor, the sakura petal canvas, the scroll-reveal animations, the typed-text hero, the skill bars, the contact form validation — all hand-written DOM code in main.js.

The reasoning: a portfolio's job is to load instantly, deploy anywhere (GitHub Pages, no CI needed), and stay readable to anyone who opens the source — including non-Vue developers evaluating whether to hire me. A build pipeline for a handful of static sections felt like solving a problem I didn't have.

The Trade-off

The cost showed up almost immediately. Things Vue gives me for free — reactive state, component boundaries, scoped styles — I rebuilt by hand with querySelectorAll, manual class toggling, and a dozen small IIFEs to keep globals from colliding. The active-nav-link highlighting alone is an IntersectionObserver I'd get from a router in about one line of Vue.

It also doesn't scale. Three sections and a contact form is comfortable in vanilla JS. If this site grows into something with real state — saved drafts, a CMS-backed writing index, anything stateful across pages — I'll hit the point where hand-rolled DOM code costs more than the framework it was avoiding.

For where this site is today, I'd make the same call again. But I'm not attached to it — the day the vanilla approach starts fighting me instead of staying out of the way, that's the trigger to rebuild it in Vue, not a reason to keep pretending the trade-off doesn't exist.
